# 红队三模块协作与旧代码迁入约定

> 2026-09-28 方案草案。首个可运行版本按 **EXPLORE（探图）→ PLACE（放弹）→ SUBMIT（提交）** 顺序执行，不做边探边放的联合优化。同学负责探图，你负责埋弹；公共运动控制由两人共同设计和验收。初赛**据队员转述的赛事组消息**没有通信拒止区；本地实现仍有 250 像素通信距离限制，不能假设每架机随时拿到全队信息。此方案不改变 `main`／`dev`／非快进合并规范。

## 1. 先明确埋弹需要什么信息

| 信息 | 用途 | 来源／负责人 |
| --- | --- | --- |
| 当前**测量**位置、朝向，必要时速度 | 判断是否已到放弹点、能否稳定放置 | 仿真器传感器；总入口读取。禁止用真值位姿。 |
| 墙证据、已知空地、未知区、地图尺寸和坐标换算 | 估计可炸墙、候选位置是否合法；不能仅凭提交用的二值墙图规划 | 探图模块提供**本机当前已融合的完整只读地图快照**。 |
| 路径可达性、预计路程、是否到达／卡住 | 从多个放弹点中选可到达者，抵达后才触发放弹 | 公共运动模块。它不知道目标来自探图还是埋弹。 |
| 本机剩余弹数、全队已确认放弹位置和库存 | 避免在同一位置重复放弹、核对是否放成功、决定何时结束 | 埋弹模块维护；通过统一通信消息传播已确认事件。 |
| 剩余步数／墙钟时间、队友位置与当前目标 | 权衡继续探图和尽快放弹；减少多机重叠 | 总入口提供时限；队友消息由总入口分发到各模块。 |
| 处置中心等语义观测、公开评分参数 | 后续估计蓝队处置难度和炸墙覆盖 | 只用本机合法观测及公开规则；难度代理须用对抗测试核对。 |

本地 `place_mapping.py` 的 M0 目前每机只有自己的墙证据。比赛中应仍由**每架无人机实例各维护一张完整的本机地图**，并把队友传来的地图增量融合进去；不存在可直接读取的“全队共用内存地图”。`snapshot()` 对本机埋弹模块呈现整张只读地图；**对无人机通信**则传增量／版本号，不必每步发送整幅数组。读地图不应允许埋弹模块原地修改探图状态。最终提交时，另由探图模块导出 `(H, W)` 的二值 `uint8` 墙图。

## 2. 三个算法模块，加一个薄总入口

| 模块与负责人 | 输入 | 输出；禁止的副作用 |
| --- | --- | --- |
| **探图**（同学；现有 `place_mapping.py`，拟增 `place_exploration.py`） | 本机观测、收到的地图消息、地图尺寸 | 更新并返回本机融合地图快照；提出下一探索目标和地图增量；导出最终墙图。**不直接下运动、放弹或提交命令**。 |
| **公共运动控制**（两人共同维护；拟增 `place_navigation.py`） | 世界坐标目标、当前测量位姿、只读地图、近距传感器 | 路径可达性／预计路程；本步 `forward`、`lateral`、`rotation` 与移动中／到达／不可达状态。**不选探索目标或放弹目标，不设置 `place_bomb`，不提交地图**。 |
| **埋弹与回合任务**（你；拟增 `place_placement.py`） | 只读地图、测量位姿、运动成本、库存、已确认炸弹、时限 | PLACE 阶段给出放弹目标；到达后请求一次放弹并核实结果；建议何时提交。**不计算雷达墙图或重复写导航算法**。 |
| **总入口／适配层**（你维护现有 `my_drone_place.py`） | 上述三个模块的结果 | 保存阶段状态，只在 EXPLORE 阶段执行探索目标、PLACE 阶段执行放弹目标；调用同一个运动模块；组装唯一 `CommandsDict`，按需设置 `place_bomb` 或提交地图；统一封装 `define_message_for_all()`。它只做调度，不再藏另一套探索／放弹算法。 |

概念上的每步顺序：读传感器与消息 → 更新本机地图 → 总入口检查阶段 → EXPLORE 时取探索目标，PLACE 时取放弹目标 → 公共运动模块驱动到所选目标 → PLACE 阶段到位后由埋弹模块请求一次放弹 → 返回最终命令。提交地图会立即结束回合，必须优先于本步运动／放弹。`place_bomb` 只在 `0→1` 上升沿生效；放置可能静默失败，需看下一步库存是否减少。现有实现要求与已有炸弹至少相距 24 像素。

“探图完成”不是仿真器提供的真值：首版将它定义为连续若干次没有可达的新前沿，**或**到达预留放弹时间之前的探索截止步数，两者先发生者触发阶段切换。截止值要给每架机移动、放完库存和最后提交留余量，不能无限等待地图完美。进入 PLACE 后只做放弹，不再切回 EXPLORE；放完且收到足够新鲜的队友库存报告，或接近安全截止时提交。炸弹难度分不能直接从墙图推出，首版先保证完整跑完和合法放置，再与参考蓝队对抗验证。

## 3. 接口契约：共享数据，不共享内部状态

建议先共同审定一份很小的 `place_types.py`（**计划文件，尚未创建**），只放数据类型和字段说明，不放算法，也不导入三个算法模块。若队友已有兼容数据类型，可复用，不必强制新建文件。

- `MapSnapshot`：世界坐标系与 `(H, W)` 行列换算、墙置信度、已知空地区、未知／已观测掩码、地图版本；只读。二值墙图是单独的提交输出，不等于完整快照。需要避免每仿真步复制整幅大图，可按版本缓存只读快照。
- `Goal`：世界坐标 `(x, y)`、来源（探索／埋弹）、所属机号和可选目标编号。目标坐标由探图或埋弹产生，公共运动模块只负责执行。
- `NavResult`：`moving`／`reached`／`unreachable`、本步运动量和可选预计路程。导航失败必须能被调用者看到，以便换目标。

探图模块需要类似 `update(observation, map_messages)`、`snapshot()`、`next_explore_goal()`、`export_wall_grid()` 的能力；运动模块需要类似 `estimate_cost(goal, snapshot)`、`step(goal, observation, snapshot)` 的能力；埋弹模块需要类似 `propose_bomb_goal(snapshot, state, cost_fn)`、`request_place_if_ready(nav_result, state)` 的能力。**这些是接口语义草案，不要求队友照抄函数名**；先对齐坐标、字段、返回值和失败行为，再按其已有代码落地。

统一通信消息由总入口组装，至少能区分发送机号、仿真步数、地图增量、探索／埋弹目标、库存及已确认放弹事件。初赛按赛事组消息暂不专门实现通信拒止区策略；不过本地代码的通信半径仍是 250 像素，超距时消息不会到达，需容许地图和炸弹记录暂时不同步。一个无人机实例的本地地图不能直接拿到另一实例的内存对象。

## 4. 首版需要实现的类、函数与回合流程

`my_drone_eval.py` 中现有的 `drone_class_for_mode("place")` 已返回 `MyDronePlace`，不需要另建评测入口。每个回合仿真器重新创建各无人机实例，每个仿真步先调用各机 `define_message_for_all()` 收集广播内容，再调用各机 `control()`；本步新增的地图增量只能在后续消息中传播。以下函数名是建议，和队友现有代码对齐时可改名，但输入、返回和副作用要固定。

| 建议类／文件 | 必需方法 | 方法职责与返回 |
| --- | --- | --- |
| `Explorer`：`place_exploration.py`，同学主责 | `update(observation, map_messages)`；`snapshot()`；`next_goal()`；`done()`；`map_delta()`；`export_wall_grid()` | 累积 GPS／罗盘／Lidar 与队友地图增量；提供本机**整张融合地图**的只读快照、下一个可达探索目标、是否无新前沿、待广播增量，以及可提交的 `(H,W)` 二值墙图。`done()` 不表示已知真值完全覆盖。 |
| `Navigator`：`place_navigation.py`，两人共管 | `estimate_cost(start, goal, snapshot)`；`step(goal, observation, snapshot)` | 估计可达性／路程；实际沿目标运动。`step` 返回运动指令及 `moving`／`reached`／`unreachable`，并负责避障、卡住恢复。不得放弹或提交。 |
| `BombPlanner`：`place_placement.py`，你主责 | `choose_goal(snapshot, pose, inventory, known_bombs, cost_fn)`；`should_place(nav_result, state)`；`confirm_placement(old_inv, new_inv, measured_pose)` | PLACE 阶段选择可达放弹目标；到位后请求 `place_bomb=1` 的**一次上升沿**；下一步以库存减少核实成功，再记录并广播大致放弹位置。失败则取消／重试该目标。 |
| `MyDronePlace`：`my_drone_place.py`，你集成 | `__init__`；`define_message_for_all()`；`control()`；`should_start_placing()`；`should_submit()` | 每架机初始化上述对象和阶段状态；组装单条通信消息；按阶段调用模块、构造唯一 `CommandsDict`；指定一架机优先提交，留备份截止。提交前确认最后一次放弹已在后续步核实。 |

回合开始时所有机处于 EXPLORE；各机独立建图与移动，按通信范围互换带机号／步数的地图增量。探索结束信号可由主要提交者广播；其他机如果暂时收不到，仍以相同的本地探索截止时刻进入 PLACE，避免无期限等待。PLACE 阶段每机根据自己当前融合地图和队友已确认炸弹记录选目标、导航、放弹并核实库存。提交者在**全队库存零的近期报告**到齐后导出自己已融合的墙图；失联或主提交者失效时按约定机号顺序错开兜底。全队一起运行同一份代码，人的分工不是比赛时由两台电脑轮流接管。

最小验收顺序：单机探图能返回墙图 → 同一个 `Navigator` 能执行探索和放弹两种来源的目标 → 单机放弹库存确实下降 → 多机地图／炸弹事件互通 → 完整回合能在时限前提交。先以当前本地地图做对照，再换出生点、地图和无人机数量。仍需运行 `./check_submission.sh` 与实际 `--competition` 回合。

## 5. 两人怎样实际协作

- `main` 只跟随官方 `origin/main`；`dev` 是验收后的团队集成分支。所有功能都从 `dev` 建分支，完成后按 `AGENTS.md` 用 `git merge --no-ff` 合回。
- 先用短分支 `feat/place-contracts` 确定地图快照、目标与运动结果的最小结构；你管理这个分支，两人审阅。接口尽早合到 `dev`，后续不随意改变字段语义。
- 同学保留其旧工程原样，在**新目录**克隆更新后的团队仓库，从 `dev` 建 `feat/exploration-import`，逐项迁入地图和探图代码。若旧入口中混有运动逻辑，把公共导航提取出来，避免整份覆盖 `my_drone_place.py`。
- 你从同一 `dev` 建 `feat/bomb-planning`，可用小型假地图和假的导航成本并行验证放弹选点，无需等待同学的探图完成。
- 公共运动模块使用 `feat/navigation-core` 及后续小主题分支：**两人共同评审接口、算法和测试，但同一时段一个改动由一人主写**；另一人审阅并提测试／修正，避免同时改同一个文件。谁已有成熟导航代码，谁先主写迁入；下一项改动可以交换主写人。
- 集成负责人由你担任：先合契约，再合最小探图和公共运动，再把最新 `dev` 合进放弹分支完成接线，最后非快进合回 `dev`。每次只合一个可运行的小增量，不把两份旧工程直接合并，也不对整份文件机械选择“保留我的／他的”。

同学若暂时不会操作 GitHub，可先保留旧目录并列出已改文件、功能和测试；在另一个干净克隆中人工迁入。克隆到**不同目录**不会覆盖旧工作。你目前本地 `dev` 领先团队 GitHub；让队友从团队远端获取本版之前，需由你手动 `git push github dev`。队友克隆 GitHub 后，他那台电脑的 `origin` 默认指向 GitHub；你本机的 `origin` 指赛事 Gitee，不能把远程别名当成全球固定名称。

每个模块独立验证输入输出；合并时重点检查：两种来源的目标都可交给同一运动模块，未知墙区不会被当成已知空地，放弹指令只触发一次且库存确实减少，队友炸弹事件可去重，任何被选为提交者的无人机都提交自己**已融合**的地图。然后运行 `./check_submission.sh`，在比赛模式跑完整回合并记录地图分、炸墙分、放弹数、耗时和异常。初赛不设通信拒止区是当前队员转述的信息，正式测试和后续阶段仍按最新赛事通知核对。
