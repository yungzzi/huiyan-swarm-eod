# 红队双人开发与旧代码迁入约定

> 2026-09-28 修订。老师确定探索同学负责**完整探图，包括探图目标、路径和运动规划**；规划同学负责**放弹与回合任务决策**。先与队友核对他已有代码的文件和提交状态；不要覆盖他的旧工程。

## 一、分工和文件归属

| 工作 | 负责人 | 主要文件 | 交付边界 |
| --- | --- | --- | --- |
| 完整探图 | 探索同学 | 现有 `place_mapping.py`；拟新增 `place_exploration.py`、`place_navigation.py` 及相应测试 | 从**合法传感器观测**更新未知／空地／墙，选探索目标、分配探索区域、规划路线、避障与脱困；输出最终二值墙图，并提供可复用的“去指定坐标”导航能力。GPS 失效后的定位可后续逐步研究。 |
| 放弹与回合任务决策 | 规划同学（仓库集成负责人） | 拟新增 `place_placement.py`、`place_coordination.py`；现有 `my_drone_place.py` 和 `my_drone_eval.py`；相应测试 | 根据**已观测**墙图选择炸弹位置，决定何时从探图切换到放弹、何时继续探图，核实库存；处理放弹／提交相关消息、失联和备选提交者。总入口只由这一人集成。 |
| 接口和最终验收 | 两人协商，规划同学执行合并 | 本文档、比赛模式验证 | 共同约定地图坐标、接口与消息格式；每次集成比较地图分、放弹数、炸墙分、耗时和失败回合。 |

`place_mapping.py` 已有 M0 基线；探索同学应在它的基础上比较、迁入已有算法，不直接用旧文件整份覆盖。`my_drone_place.py` 是共享入口，原则上由放弹同学维护。探索同学若已有入口改动，先列出其中的算法和传感器调用，把可复用逻辑迁到自己的模块，再由入口负责人接线。放弹同学也不直接修改探图模块内部算法；发现问题用接口和测试讨论。

探索同学负责“墙在哪里、下一块探哪里、怎么过去”；放弹同学负责“去哪放弹、何时放、何时提交”。放弹同学不再另写 A* 或底层路径跟踪；到放弹点的运动复用探索同学提供的导航接口。炸弹难度分需要蓝队评估才能证实，不能只以炸墙覆盖率代替。地图提交仍须是 `uint8`、形状 `(H, W)` 的二值墙图。

## 二、先约定一条最小接口

先以数据语义约定，函数名可在首次集成时确定：

- 输入观测：本机测量位姿、Lidar 距离与相对角、语义结果、当前步数；不能读取真实位姿或地图真值。
- 地图快照：世界坐标与栅格坐标的换算；每格的未知／空地／墙状态及可信度。放弹模块只读，不原地修改地图模块的数组。
- 探图动作：探索模块自己选前沿、规划路径并返回本步运动指令；它不设置 `place_bomb`，也不调用 `submit_exploration_map()`。
- 指定目标导航：放弹模块提供世界坐标 `(x, y)`，探索同学的导航模块返回朝该目标移动的本步指令，以及已到达／不可达状态。复用同一套避障与脱困逻辑。
- 提交墙图：`(H, W)` 的二值数组；只由控制入口在决定结束回合时调用 `submit_exploration_map()`。
- 通信：地图增量、探索目标及其来源／步数由探索模块提供；库存、放弹目标和提交者状态由放弹模块负责。由总入口统一组装一条消息。消息可能延迟或丢失，不能依赖每步全员在线。

总入口的调用顺序约定为：读取观测并更新探图模块 → 放弹模块决定本步是继续探图、驶向放弹点还是提交 → 选择探图运动或指定目标导航 → 放弹模块设置 `place_bomb` → 返回本步命令。提交优先于本步运动／放弹；一次只有一个模块给出最终运动命令。

接口先用一张最小地图、一架无人机跑通，再扩展到多机。各自提交的小测试验证坐标方向、未知状态、不可达目标和无通信时的行为。

## 三、把探索同学已有代码安全迁入

1. **保留旧目录原样。** 先记录旧工程的 `git status`、当前分支、最近提交和修改文件清单；未提交的有用源码先在旧工程自己的临时分支提交或另外备份。不要在旧目录直接执行会覆盖文件的操作。
2. 规划同学先把当前 `dev` 推送到团队 GitHub。当前本地 `dev` 领先 `github/dev`，队友若现在克隆，拿不到最新 M0。推送命令为 `git push github dev`；这会发布 `dev` 上全部尚未推送的提交。
3. 探索同学**另建一个新目录**克隆团队 GitHub 仓库，切到 `dev`，再建 `feat/exploration-import`。新目录克隆不会触碰旧工程；克隆后的远程名通常是 `origin`，与规划同学电脑上指向赛事 Gitee 的 `origin` 含义不同，先用 `git remote -v` 核对。
4. 从旧目录逐项迁入算法和测试。优先复用独立函数；若旧代码改过 `my_drone_place.py`，不要整份复制覆盖，改为提炼到探索模块，并给入口负责人一份需要接入的调用说明。每迁入一项就运行测试、提交一次，避免一个巨大提交。
5. 若旧工程与团队仓库**确有共同 Git 历史**、已有小而独立的提交，可考虑逐个 `cherry-pick` 到新工作分支；若历史不同或冲突过多，按第 4 步人工迁入更容易核对。不要用 `--allow-unrelated-histories` 强行合并两棵树，也不要为了通过合并选择整份“保留我的／保留他的”。
6. 若探索同学暂时不会使用远程，可先在旧工程完成源码和测试，由规划同学在自己的独立导入分支迁入并注明原作者；这是过渡方法，后续仍建议让他学会从团队 `dev` 建分支和推送自己的分支。

## 四、固定的分支与合并顺序

- `main`：只同步官方 Gitee；不放团队开发代码。
- `dev`：团队集成线；只有集成负责人在检查后更新，不直接写功能代码。
- `feat/exploration-import`：探索同学迁入旧成果的第一支；之后新任务用 `feat/exploration-<主题>`。
- `feat/bomb-mission`：放弹同学从同一个 `dev` 开始写放弹、回合任务和提交模块。两人的工作分支不要共用同一个工作目录，也不要同时修改总入口。

**第一次集成顺序：**先锁定接口；探索分支完成最小可用建图／前沿测试后，由规划同学检查并 `git merge --no-ff` 合入 `dev`；规划同学再把更新后的 `dev` 合入自己的规划分支、解决接口冲突并验证，最后用 `git merge --no-ff` 合回 `dev`。每次只合一个可运行的小功能，不等到两人全部写完才首次集成。官方更新沿仓库 `AGENTS.md` 的独立同步流程进入 `main`，再非快进合入 `dev`。

放弹同学现在即可从本地 `dev` 建 `feat/bomb-mission`，独立实现一个只使用**观测地图**的放弹候选点评分函数，并用小地图测试“靠近可炸墙、少与既有炸弹重复、目标可达”这三项。先让函数返回候选坐标与评分，不改当前总入口的定时放弹；待探图导航接口合入后，再接入“驶向目标 → 尝试放弹 → 核实库存”的闭环。探索同学同时迁入旧代码并完成探图与指定目标导航。这样两人不用等待对方，也不会同时改 `my_drone_place.py`。

```bash
git switch dev
git switch -c feat/bomb-mission
```

`git switch -c` 是从当前 `dev` 创建并切换到一个新的本地工作分支；它不会修改远端仓库。

探索同学在新克隆目录中，从团队 `dev` 开始：

```bash
git remote -v                 # 先确认 origin 指向团队 GitHub
git switch dev                # 切到团队集成分支
git switch -c feat/exploration-import
# 迁入旧代码中的独立功能、验证后，按用途 git add / git commit
git push -u origin feat/exploration-import
```

规划同学在自己的仓库中负责第一次集成；下面的 `github` 是本机给团队 GitHub 起的远程别名：

```bash
git fetch github
git switch dev
git merge --no-ff github/feat/exploration-import
./check_submission.sh
git push github dev
git switch feat/bomb-mission
git merge --no-ff dev       # 把已合入的探图与导航接口带进放弹分支
# 完成放弹模块及集成验证后，再切回 dev 做非快进合并
```

`git push -u` 在首次推送工作分支时设置远程跟踪关系；`git merge --no-ff` 保留显式合并记录。若合并提示冲突，先停下核对，不要在未理解代码含义时直接选择整份文件。

冲突时以**当前接口契约和仿真结果**判断代码，不机械选择任一方版本：探索文件由探索同学解释意图，入口／规划文件由规划同学负责整合；改动同一文件的冲突由两人一起确认。合并前至少运行相关单元测试、`./check_submission.sh`，集成后在比赛模式跑完整回合并检查地图提交、库存和成绩。只有合入并验收的 `dev` 才是团队当前版本。

## 五、队友只需先掌握的远程 Git 概念

- `clone`：在**新目录**取得团队仓库；不会覆盖另一个旧目录。
- `remote`：远程仓库的本机别名；`origin` 只是默认名字，不一定是赛事官方仓库。
- `fetch`：下载远端分支信息，不自动改当前工作文件；`pull` 还会尝试把远端变化合入当前分支。
- `branch` / `switch`：每项工作建自己的分支；提交到本地不等于别人能看到。
- `push`：把自己的工作分支上传供集成负责人查看；不要直接推 `main` 或 `dev`，不要对团队分支强制推送。

权限方面，团队 GitHub 仓库若为私有，仓库所有者需邀请探索同学为 collaborator。他有写权限后仍按上述分支约定协作；仓库管理与最终合并由规划同学负责。
