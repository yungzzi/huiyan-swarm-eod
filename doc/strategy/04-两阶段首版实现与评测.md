# 两阶段首版：实现、替换接口与本地评测

日期：2026-10-02。方案依据：[完整理论方案](./03-多机探索建图与分阶段布弹理论.md)。

**已实现并运行的是一份可继续开发的基线：多机先探索建图，有限时间汇合交换信息，再各自布弹并提交。**本版完全使用我们自己的策略，没有接入队友代码。队友后续可替换探图或导航模块，保留布弹模块和赛事入口。

## 1. 理论是否足够完整

理论已经覆盖第一版必需的闭环：合法观测、地图表示、探索目标、机间信息交换、运动执行、放弹确认、阶段切换、超时提交和官方指标。它足够支撑一个可运行、可评测的版本。

但“闭环完整”不代表“已得到最优策略”。原理论中的联合选点、任务分配、路线优化和蓝队难度代理，在数学上仍依赖近似与实验；本版先实现较简单的分布式贪心策略。不能把最大覆盖问题的经典近似结论直接套到本版：这里还存在估计地图、通信不完整、路径预算和库存约束。

| 理论内容 | 本版落实程度 |
| --- | --- |
| 多机感知、坐标统一、各机地图融合 | 使用带噪 GPS、罗盘和 Lidar，按来源版本融合墙证据；不是完整协同 SLAM |
| 探索决策 | 前沿聚类；附近未知格数量、路程、机号方向偏好、队友目标冲突惩罚 |
| 通信 | 实际调用仿真器通信器；保留来源和版本，程序显式转发已收到的信息 |
| 探索完成与阶段切换 | 统一固定步数预算；尚未实现全队覆盖充分性判定与自适应切换 |
| 布弹选点 | 估计地图上的新增炸墙覆盖，扣除已知炸弹及近期队友目标的覆盖，并惩罚路程 |
| 多机任务分配 | 各机独立选点，加目标预留与已确认事件；没有集中式联合分配或全局排路线 |
| 安全执行与确认 | 共享导航、近距避障、卡住换目标、放弹上升沿、下一步库存减少确认 |
| 提交与兜底 | 全队零库存消息到齐后提前提交；否则按步数或墙钟时限兜底 |
| 蓝队处置难度 | 尚未建模，尚未运行参考蓝队对抗；本地红队运行不能产出这 20% 得分 |

第一版允许使用 GPS 辅助建图，因为本次配置没有 GPS 或通信拒止区。定位丢失时导航停止并返回 `unavailable`，保留截止提交；这只是兜底，不是 GPS 拒止下的完整定位方案。

## 2. 文件与每步调用

所有策略文件位于 `src/swarm_rescue/solutions/`。

| 文件 | 职责 |
| --- | --- |
| `my_drone_eval.py` | 原有赛事入口；PLACE 模式已选择 `MyDronePlace`，本次不需要修改 |
| `my_drone_place.py` | 薄适配层：读合法传感器、处理消息、切换阶段、调用模块、组装唯一动作、提交 |
| `place_types.py` | 数据类型与探图、导航契约；队友首先阅读此文件 |
| `place_mapping.py` | 沿用已有单机墙证据更新；本次未修改 |
| `place_exploration.py` | 本机建图、来源版本融合、前沿目标、只读地图快照、导出墙图 |
| `place_navigation.py` | 两种任务共用的路径成本、缓存 A*、反馈运动、近距避障与卡住检测 |
| `place_placement.py` | 布弹选点、预留去重、放弹请求、库存确认和事件记录 |

~~~text
每回合开始：官方 launcher
  → my_drone_eval.drone_class_for_mode("place")
  → 创建各机 MyDronePlace
       ├─ Explorer：各机自己的本机及融合地图
       ├─ Navigator：各机自己的导航缓存
       └─ BombPlanner：各机自己的库存确认、目标和事件记录

每个仿真步：
  官方 GUI 更新循环
    → 各机 define_message_for_all()：广播此前一步已获得的信息
    → 各机 control()
         1. _observe()：合法传感器 → Observation
         2. _receive()：收到的地图、队友状态、已确认炸弹
         3. BombPlanner.confirm()：核对上一步放弹是否成功
         4. 阶段判断；EXPLORE/SYNC 调 Explorer.update()
         5. Explorer.snapshot()：本机当前融合地图
         6. 截止或全队零库存到齐？导出并提交，结束回合
         7. 选择当前任务：
              EXPLORE → Explorer.next_goal()
              SYNC    → 分散汇合点
              PLACE   → BombPlanner.choose_goal()
              已放完  → 回汇合点传播库存、地图和事件
         8. Navigator.step()：执行目标 → NavResult
         9. 仅 PLACE 且到达、速度合适时 BombPlanner.request()
        10. 返回运动指令，必要时 place_bomb=1
~~~ 

各机运行相同代码，没有跨实例的全局共享地图。模块对象在本机内直接调用，**跨无人机的信息必须经过通信器**。消息可以转发，但不会因为它们运行在同一台电脑上就自动互通。

## 3. 第一版的阶段预算

以该地图的最大仿真步数 $T$ 为基准：

| 阶段 | 范围与动作 |
| --- | --- |
| EXPLORE | $0 \leq t < 0.40T$，主动探索并更新地图 |
| SYNC | $0.40T \leq t < 0.54T$，回分散汇合点，继续观测和交换地图 |
| PLACE | $t \geq 0.54T$，不再主动探索；按当前地图选点、导航、放弹 |
| 布弹选点预算 | 以 $0.90T$ 为移动预算截止；为确认与提交留余量 |
| 提交兜底 | $t \geq 0.95T$，或墙钟时间达到限额的 92%，且没有待确认放弹 |

PLACE 阶段停止生成新的本机建图证据；仍可接收其他机探索期间的迟到地图，因此融合快照版本可能继续变化。实时 Lidar 仍用于运动避障。进入 PLACE 不保证每机都拿到了相同的全队地图。

每机每枚放弹先产生一次请求，下一步只有库存减少才记录成功。两次请求至少间隔 6 步，确保中间有 `place_bomb=0`。本版采用 64 像素规划间距，为官方当前 24 像素最小间距和测量误差留余量；这不能代替仿真器的实际放置检查。

已确认的零库存不会因为消息变旧而失效：本回合库存不能增加。收到全队零库存并等待短暂传播后可以提前提交；缺少某架机的报告时仍等待截止兜底。

## 4. 队友需要实现的接口

### 4.1 数据语义先固定

`place_types.py` 是唯一共享契约文件。队友不需要继承 `DroneAbstract`，也不需要自己拼赛事 `CommandsDict`。

| 类型／字段 | 约定 |
| --- | --- |
| `Observation.position` | 合法测量世界坐标 $(x,y)$，单位像素；可能为 `None` |
| `heading` | 世界朝向，弧度；可能为 `None` |
| `velocity` | 当前 API 的测量位移增量，按每仿真步解释，单位像素／步；不要直接当成像素／秒 |
| `lidar`、`angles` | 同长度数组；距离像素，相对机体角度为弧度；不得为导航方便而修改原始雷达数据 |
| `nonwalls`、`bomb_returns` | 合法语义观测得到的非墙及炸弹回波；用于区分地图更新和运动避障 |
| `inventory`、`step` | 本机当前剩余炸弹和当前仿真步数 |
| `Goal` | 世界目标坐标和来源字符串：`explore/place/sync/report` |
| `NavResult` | `moving/reached/unreachable/unavailable` 及本步运动指令 |
| `MapSnapshot.wall_grid` | 精细二值墙图，`uint8`，形状 $(H,W)$，1 表示估计墙 |
| `known/blocked/wall_mass` | 同形状粗网格：已观测掩码、导航障碍、用于覆盖估计的精细墙加权数量 |
| `version` | 任意地图内容变化必须提升版本，用于缓存失效 |
| `cell()/world()` | 世界坐标与粗网格行列互换；世界 x 向右、y 向上，数组行向下、列向右 |

地图数组应只读。调用者需要临时计算时先 `.copy()`。`wall_mass` 不含导航膨胀；不要把为机器人安全扩大后的墙当成可炸墙面积。

本版粗网格分辨率为 16 像素。一个格里只要有观测证据就标记 `known`；这是低分辨率近似，不能解释成格内每个像素都已验证为空地。完全未知的粗格不参与路径搜索，近距 Lidar 处理运行时障碍。

### 4.2 Explorer 契约

构造：`Explorer(size, identifier, team_size)`，其中 `size=(W,H)`。

| 接口 | 返回／职责 |
| --- | --- |
| `anchor` | 第一个可用测量位置，或 `None`；供汇合使用 |
| `update(observation)` | 更新本机观测和地图，返回 `None` |
| `ingest(source, version, payload)` | 接收并融合一个来源的地图贡献 |
| `map_delta()` | 返回 `(source, version, payload)` 或 `None`；必须保留真实来源与版本 |
| `snapshot()` | 当前完整的本机融合 `MapSnapshot` |
| `next_goal(observation, navigator, peers)` | 下一探索 `Goal`，没有可行目标时返回 `None` |
| `reject(goal, step)` | 导航失败后暂时避开该探索目标 |
| `export_wall_grid()` | 可提交的精细 $(H,W)$ 二值墙图 |

**当前 `map_delta()` 名称沿用接口约定，但载荷是单个来源的压缩完整证据快照，并非少数格子的增量。**每机用来源机号、版本替换该来源的旧贡献；转发不会重复累加。同一来源新版本可以修正旧墙，不是只做墙图按位或。

当前线上格式是按行排列的 `int8 (H,W)` 证据数组，范围 $[-8,8]$，用 zlib 压缩。每 24 步形成本机新版本，每 12 步轮流发送一个已有来源。队友替换 Explorer 时，应兼容这个格式，或双方一起修改协议与解析，不能只换发送端。

### 4.3 Navigator 契约

构造：`Navigator()`。

| 接口 | 返回／职责 |
| --- | --- |
| `distance_field(start, snapshot)` | 与粗地图同形状的最短路径距离数组，单位像素，不可达为 `np.inf` |
| `estimate_cost(start, goal, snapshot)` | 单目标估计路程，不可达或越界返回 `math.inf` |
| `step(goal, observation, snapshot)` | 一个 `NavResult`；不放弹、不提交、不更新探图地图 |
| `reset()` | 清除当前执行目标和路径状态 |

本版距离场用 Dijkstra，实际执行路径用缓存 A*；八邻域不穿墙角。反馈控制把世界目标转成机体前进／横移量，叠加速度阻尼和 Lidar 排斥。到达状态不等于仿真器保证放弹成功，仍需库存确认。

红队新放的炸弹在当前官方代码中忽略无人机碰撞，因此导航可忽略对应炸弹回波。建图仍保留原始雷达数据，不能把炸弹遮挡后面未经观测的空间凭空清为空地。

### 4.4 怎么接入队友实现

队友先从最新版 `dev` 创建自己的功能分支，迁入兼容类，例如 `teammate_exploration.py` 中的 `TeammateExplorer`。总入口只有三处工厂负责创建模块：

~~~python
class MyDronePlace(DroneAbstract):
    explorer_factory = staticmethod(Explorer)
    navigator_factory = staticmethod(Navigator)
    planner_factory = staticmethod(BombPlanner)
~~~

接入时引入队友的类，把相应工厂改为 `staticmethod(TeammateExplorer)` 或 `staticmethod(TeammateNavigator)`。如果构造参数或内部方法不同，写一个小适配类，转换为上述契约；不要整份覆盖总入口、修改官方 launcher，或把埋弹决策重新写进探图模块。

`staticmethod` 让类上的工厂按普通构造函数调用，不会把 `MyDronePlace` 实例额外传成第一个参数。两人的接口修改先共同审阅 `place_types.py`，再分别改实现和有行为意义的测试。

## 6. 自己运行或看回放

在工程根目录运行：

~~~bash
export GALLIUM_DRIVER=d3d12
export MESA_D3D12_DEFAULT_ADAPTER_NAME=nvidia
.venv/bin/python -m swarm_rescue.launcher --competition -c config/local_two_phase_eval.yml
~~~

两条 `export` 仅设置当前终端会话的图形驱动与优先显卡。`.venv/bin/python` 明确使用本工程解释器，不要求先激活虚拟环境。`-m` 按 Python 模块启动官方 launcher；`--competition` 启用比赛运行；`-c` 选择本地两图测试配置。上述命令带可视化窗口，省略了验证时用于无界面运行的 `--headless`。

配置每张图只跑一回合，并保存回放。平常直接运行会使用新的随机状态；要精确按本次种子复现：

~~~bash
.venv/bin/python -u -c 'import random, numpy as np, runpy, sys; random.seed(17); np.random.seed(17); sys.argv=["swarm_rescue.launcher", "--competition", "--headless", "-c", "config/local_two_phase_eval.yml"]; runpy.run_module("swarm_rescue.launcher", run_name="__main__")'
~~~

`-u` 使日志及时输出；`-c` 在这里是 Python 的“执行这段代码”，与 launcher 配置参数是两个层级。代码先固定两个随机源，再按同一个官方入口运行。墙钟耗时会受电脑负载影响，因此依赖墙钟截止的回合仍可能出现差异。

如果只想看本次已经发生的过程：

~~~bash
.venv/bin/python -m swarm_rescue.launcher --replay results_swarm_rescue/team006_261002_22h37min23s/recordings/team006_Map01_none_rd1.npz
~~~

把文件名中的 Map01 换成 Map02 就能看第二张图。回放是播放状态记录，不重新执行策略或产生新的成绩。

## 7. 目前短板与下一步

1. **汇合与结束协议。**Map01 的最后一枚在第 1389 步已确认，但没有任意一机及时拿齐全队零库存报告，直到第 1900 步兜底提交。出生锚点附近的偏移汇合点可能不可达；下一版应在已知空地选可达汇合区域，并给提交者发送有确认的阶段报告。
2. **布弹覆盖与路线联合优化。**独立贪心即使有预留也可能重叠；Map02 炸墙分仅 44.7。应先比较候选点集合、联合覆盖和机位／库存分配，再优化路线，避免只改一个覆盖权重。
3. **建图误差和汇总。**带噪 GPS/罗盘直接累积会让墙增厚。这里只做按来源去重，不处理多机观测相关性，不做 ICP、位姿图或回环；需要队友更好的探图／定位实现替换。
4. **通信成本。**完整压缩源地图较容易正确去重，但带宽与融合计算仍可优化。同步也只是尽力交换，没有全队版本一致性确认。
5. **评测覆盖。**下一轮补剩余地图与多个随机种子，记录失败率与分项分布；然后加入参考蓝队难度测试。当前两回合不能证明所有地图、机数或拒止区域都适用。

推荐先改善可达汇合和提前提交，再优化布弹路线，随后接入队友探图。保留这版作为可运行对照，每次改动都用相同配置和种子比较，避免仅凭窗口“看起来跑得不错”判断。
